# AMR 관제 시스템 사용자 시나리오

사용자 행동과 관찰할 결과를 정의한다. 현재 콘솔/대역 실습과 후속 시나리오를 구분한다. 예시·기대값은 절차이며 실제 실행 로그가 아니다.

이 문서는 현 저장소의 SC 실습 안내다. 신규 개발의 원문 통합 인수는 개정0.3 [기능명세](../full/feature_spec.md)의 INT-01~04이며, 정책은 [PDF 비교서](../full/pdf_comparison.md)의 P-01~21을 따른다. SC-001/002 통신 대역 시험이 전체 통합 인수를 대체하지 않는다.

## SC-001 두 AMR 생존과 중단 감지

검증 담당자가 한 AMR의 중단이 다른 AMR 감시에 영향을 주는지 확인한다. 현재 콘솔/TestClient로 검증된 범위다. 사전 조건은 Broker, 빌드된 수신 콘솔, 서로 다른 ID의 TestClient2대다. 실행 명령은 [README](development.md)를 따른다.

| 단계 | 사용자 행동 | 시스템 동작 | 확인 |
| --- | --- | --- | --- |
| 1 | 콘솔과 A/B 실행 | 첫 정상 Heartbeat부터 각각 감시 | 두 ID 감시 시작 |
| 2 | A만 중단 | 마지막 정상 수신부터 시간 계산 | A Timeout1회, B 수신 지속 |
| 3 | 같은 ID로 A 재실행 | 정상 재수신 복구 | A 복구1회 |

불량 Heartbeat는 시각을 갱신하지 않아야 한다. COM-02의7항목·증거가 합격 기준이다. GUI의 최종 Offline 판정은 현재 범위 밖이다.

## SC-002 역순 명령 결과 연결

응답 순서가 바뀌어도 대상 요청이 섞이지 않아야 한다. 기본 왕복은 존재하며 COM-05 전체 검증은 미완료이며 전체 개발 순서는 1차 MVP 계획을 따른다. 사전 조건은 실제 Broker, 요청 목록 Core 대역, 응답 순서를 제어하는 AMR2대다.

| 단계 | 시험 행동 | 시스템 동작 | 확인 |
| --- | --- | --- | --- |
| 1 | A에 ID1, B에 ID2 요청 | 요청 보관·발행 | 수신 ID·대상 일치 |
| 2 | B의 ID2 FAILURE 먼저 반환 | 원형 전달 | B/ID2 요청에만 연결 |
| 3 | A의 ID1 SUCCESS 나중 반환 | 원형 전달 | A/ID1 요청에만 연결 |
| 4 | cmdId 없는 ACK 발행 | 검증 로그·폐기 | Core 전달 없음 |

기대 관측은 `B / ID2 / FAILURE / 원래 이유`, `A / ID1 / SUCCESS`다. SUCCESS는 응답 대역의 시험값으로 실제 이동 완료가 아니다. 세 명령 유형과 전체7항목은 [Iteration01](../full/iteration_01.md)에 있다.

## SC-003 이동과 Telemetry

관제 사용자가 목표 좌표를 요청하고 경과·결과를 확인한다. 이동·Telemetry 생성은 후속이다. 사전 조건은 설정 기반 AMR과 P-02/03/07의 상태·ACK·좌표 정책이다.

| 단계 | 사용자 행동 | 목표 동작 | 확인 |
| --- | --- | --- | --- |
| 1 | 허용 상태에서 MOVE | BUSY·이동 계산 | 요청 ID 추적 |
| 2 | 이동 관찰 | 실제 좌표·속도·상태 발행 | 내부 값과 Telemetry 일치 |
| 3 | 도착 확인 | 정한 도착 기준, IDLE·완료 ACK | 완료 전 성공 없음 |
| 4 | 새 이동 중 STOP | 정지·각 요청 결과 처리 | 정지 후 좌표 고정 |

허용되지 않은 명령은 이유와 함께 거부한다. STOPPED 재출발·원래 MOVE 중단 결과는 정책 확정 후 기대값을 고정한다. 합성 Telemetry 수신 통과로 완료 처리하지 않는다.

## SC-004 장애 Alarm과 복구

장애를 확인하고 원인 해소 후 복구한다. 실제 장애·Alarm 생성은 후속이다. 사전 조건은 장애 설정·P-04 전이·RESET 허용 조건이다.

| 단계 | 사용자 또는 시험 행동 | 목표 동작 | 확인 |
| --- | --- | --- | --- |
| 1 | A 장애 발생 | ACTIVE Alarm·장애별 상태/제한 | 실제 code/level/상태 일치 |
| 2 | 제한된 MOVE 요청 | 이유 포함 FAILURE | 같은 cmdId로 연결 |
| 3 | 원인 지속 RESET | 복구 실패 | 거짓 정상 복구 없음 |
| 4 | 원인 해소 후 RESET | 정한 순서의 복구·CLEARED·결과 | 장애 기록·최종 상태 일치 |

CLEARED와 RESET 순서는 결정 대기다. A의 장애가 B의 상태를 바꾸지 않아야 한다. 파서는 메시지를 전달하고 운행 상태는 AMR/Core 계약으로 결정한다.

## SC-005 Broker 중단과 복구

Broker 재시작 후 프로그램 재실행 없이 통신을 회복한다. 현재 자동 복구는 미구현이다. 사전 조건은 P-05 정책과 양측 재접속·재구독 구현이다. 공유 Broker 대신 독립 시험 Broker를 사용한다.

| 단계 | 시험 행동 | 목표 동작 | 확인 |
| --- | --- | --- | --- |
| 1 | Broker 중단 | 단절 감지·이전 세션 종료 | 원인·감시 종료 |
| 2 | Broker 재시작 | 정책에 따라 재연결·재구독 | 프로그램 재실행 없음 |
| 3 | 새 명령·Heartbeat | 새 세션 송수신 | 누락 구독·중복 소비자 없음 |

단절 전 요청의 재전송·결과 정책은 별도다. Broker 복구만으로 이전 명령 성공을 주장하지 않는다.

## SC-006 GUI 요청과 이력 조회

등록 장비를 화면에서 선택하고 명령·장애·이력을 확인한다. 실제 Core/GUI/SQLite 통합은 후속이다. 사전 조건은 실제 Core, 등록 장비, 저장소와 화면 계약이다.

GUI 대상·명령 입력 → Core 검증·요청 등록 → Communication 전달 → 실제 AMR 결과 → Core 저장·상태 갱신 → GUI 표시 → 재시작 후 조회 순서로 확인한다.

성공 기준은 AMR/cmdId의 전 단계 일치, 등록/통신/운행 상태 구분, 재시작 후 이력 보존이다. 입력 오류·저장 실패·ACK 미수신은 정한 정책대로 표시한다. GUI의 직접 MQTT/DB 실험 코드는 완료 근거가 아니다.

# 공통 규칙 작성 재개 메모

작성일 2026-10-01. 다음 작업일은 2026-10-02다. 받은 과제를 해석해 작성한 PDF에서 공통 규칙을 정리하기 위한 작업 메모다. 내일의 목표는 **AMR 식별·시간·Alarm 세 항목을 같은 양식으로 작성하고, 근거와 적용 상태를 설명할 수 있게 하는 것**이다.

## 오늘 정리한 문서 관계

- 받은 「가상 AMR 관제 시스템 단계별 개발 과제 구성」은 개발 목표와 결과물을 제시하는 원본이다. 이 문서의 ‘공통’은 과제 1~5 전체에 대한 요구사항·기능명세 작성 작업이다.
- 직접 작성한 「요구사항 정의 및 기능명세 이인호 연구원 v0.3」은 원본을 구체화한 문서다. 개요·공통 규칙·메시지 형식·설계·기능·검증 계획이 함께 들어 있다.
- 공유 규칙은 여러 모듈이 같은 의미로 처리해야 할 조건이다. 한 클래스 내부의 구현 방법은 해당 기능의 설계에 기록한다.

내용은 개요와 범위 → 공통 규칙 → 데이터 계약 → 시스템 설계 → 기능명세 → 검증 계획과 결과로 배치한다. 이 순서는 내용의 묶음이며, 묶음마다 새 파일을 만들 필요는 없다. 기존 [PRD](../full/prd.md)와 [공통 계약](../full/interface_contract.md)을 활용하고, 내일은 먼저 초안의 내용과 근거를 정리한다.

## 초안과 상세를 구분하는 기준

‘정의’는 의미와 기준을 명확하게 적는 작업이다. ‘초안’과 ‘상세’는 서로 다른 기준이므로 상세하게 작성한 규칙도 검토 중인 초안일 수 있다.

| 구분 기준 | 표시할 내용 |
| --- | --- |
| 설명 수준 | 기본 규칙 / 상세 규칙 |
| 적용 상태 | 초안·제안 / 검토 필요 / 채택. 채택한 개발값에는 개발용 임시와 적용 범위를 표시 |
| 근거 | 받은 과제 원문 / 작성한 PDF의 정의 / 과제에서 도출 / 기존 개발 결정 |

자료에 적혀 있다는 사실과 적용하기로 채택했다는 사실을 구분한다. 기존 계약은 그 적용 범위에서 유지하고, 아직 채택하지 않은 제안을 전체 시스템의 확정값으로 쓰지 않는다.

## 내일 작성할 양식과 예시

각 항목에 **규칙명, 기본 규칙, 상세 규칙, 필요한 이유, 출처, 적용 모듈, 상태와 범위, 미정 사항**을 적는다. 아래 예시는 이해와 검토를 위한 초안이며 새 정책을 채택하는 기록이 아니다.

| 항목 | AMR 식별 | 시간 | Alarm |
| --- | --- | --- | --- |
| 기본 규칙 | 동일 AMR을 설정·메시지·Core·GUI·이력에서 같은 ID로 식별한다. | 발생 시각과 관제 수신 시각을 구분하고 공통 형식·단위를 사용한다. | 코드·등급·발생/해제 상태의 의미를 모듈 간 동일하게 해석한다. |
| 상세 규칙 | Payload에 id가 있으면 Topic ID와 일치해야 한다. ACK의 id는 현재 수신 계약에서 선택이다. | 현재 통신 계약은 Int64 Unix 밀리초다. Heartbeat 경과 시간은 정상 수신 시점의 단조 시계로 판단한다. | AMR이 Alarm을 생성하고 Communication이 검증·전달하며 Core가 업무 상태와 이력을 관리하고 GUI가 표시한다. |
| 필요한 이유 | 다른 장비의 데이터·결과가 섞이는 것을 방지한다. | 시간 단위 오해와 원격 시계·처리 지연에 따른 감시 오류를 줄인다. | 발생 데이터와 표시·처리 판단을 일치시킨다. |
| 출처 | 작성한 PDF p3~4·6, 기존 DN-02 | 작성한 PDF p3·5~6, 기존 DN-02·10 | 받은 과제의 가상 AMR·통신·Core 요구, 작성한 PDF p4~6·11·16 |
| 상태와 범위 | 통신 ID 검사는 기존 개발 계약에 적용. Core·GUI·DB 전체 연동은 후속이다. | 밀리초와 Heartbeat 개발값은 임시 채택. 전체 운영값 확정이 아니다. | 형식 검증은 기존 계약에 적용. 실제 장애 생성·Core·GUI 전체 Alarm 관리는 후속이다. |
| 미정 사항 | 미등록 AMR의 등록·거부 정책 | 화면 시간대·운영 주기·Timeout | 발생/해제 조건·State 전이·RESET 관계 |

Alarm 표의 코드·등급·State·명령 영향은 공통 업무 의미로 정리한다. 장애물 거리·유지시간은 가상 AMR의 시나리오 설정 또는 기능명세에 둔다. 여러 모듈이 같은 임계값을 판단해야 하는 경우에는 공통 계약으로 관리할 필요를 검토한다.

작성한 PDF의 Alarm 표는 예시다. 해제조건 ‘거리 0.7m’에는 부등호·유지시간이 없고, 충돌 해제 후 STOPPED·RESET 후 IDLE·Heartbeat 이상과 비상정지의 관계도 확인이 필요하다. 이를 임의로 확정하지 않고 미정 사항에 적는다.

## 내일 작업 순서와 완료 기준

1. 이 메모를 읽고 원본 과제의 ‘공통’과 모듈의 ‘공유 규칙’을 구분한다.
2. [PRD 6절](../full/prd.md#6-공통-요구사항)과 [공통 계약](../full/interface_contract.md)에서 AMR 식별·시간·Alarm 부분만 읽는다.
3. 위 세 항목을 양식에 맞춰 자신의 말로 고친다. 기본 규칙과 상세 규칙을 구분하고 각 내용에 출처를 붙인다.
4. 기존 채택값은 [수신 계약](../../src/Amr.Communication/Validation/CONTRACT.md)과 [감시 계약](../../src/Amr.Communication/Monitoring/CONTRACT.md)을 대조한다. 충돌·누락은 [PDF 비교서](../full/pdf_comparison.md)의 결정 필요 사항과 연결한다.
5. 각 항목이 왜 필요한지 설명해 보고, 모르는 부분은 미정 사항으로 남긴다. 합의 후 기존 문서에 반영할 위치를 정한다.

완료 기준은 **세 항목에 기본·상세 규칙, 근거, 적용 범위, 상태, 미정 사항이 있고 본인이 이유를 설명할 수 있는 것**이다. 상세 수치를 전부 확정할 필요는 없다. 작업이 끝나면 나머지 목록을 같은 양식으로 이어간다.

현재 COM-01~04는 기존 계약 범위에서 passing이며 COM-05 전체 검증은 미완료다. 이 메모 작성은 기능 구현·검증이나 요구 변경이 아니다. COM별 설계·결과 보고는 공통 규칙을 정리한 다음 기존 증거와 연결한다. 현재 상태는 [진행 기록](../../claude-progress.md), 공식 계약·상태는 [기능 추적기](../../feature_list.json)를 따른다.

다음 대화는 이렇게 시작하면 된다: **“공통 규칙 작성 재개 메모를 읽고, AMR 식별·시간·Alarm 세 항목을 내 말로 정리하는 것부터 같이 하자.”**

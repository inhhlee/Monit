# 가상 AMR 관제 시스템 요구사항 정의서

문서 버전0.3, 작성일2026-09-30. 개발·검증·기획 담당자에게 전달할 **전체 제품의 목표 요구사항**이다. 기존 코드를 모르는 개발자도 무엇을 만들어야 하는지 알 수 있도록 기술한다. 현재 구현 상태는 [PDF 비교서](pdf_comparison.md)로 분리했다. 0.3은 전체 요구를 유지하면서 1차 MVP와 2차 개발 범위를 구분한 개정이다.

## 1. 문서 목적과 기준

원본은 2026-09-17자 「요구사항 정의 및 기능명세 - SI생태계」 v0.3,17페이지다. 기능 표의23개 ID를 유지하고 p15 도식의 CORE-06을 보완한다. 원문 요구, 기존 개발 결정, 도출·제안, 결정 필요 사항을 구분한다. 파일 해시·페이지 대응·충돌은 비교서에 기록했다.

이 문서는 신규 개발을 위한 검토용 명세다. 현재 저장소의 실행 계약·합격 상태를 소급 변경하지 않는다. 새 정책 채택 시 추적기 revision·설계 결정·검증을 먼저 갱신한다. 특정 클래스명·기존 테스트 개수·passing 상태를 요구사항으로 사용하지 않는다.

## 2. 제품 목적

가상 AMR의 이동·운행 상태·장애·명령 결과를 시뮬레이션하고 MQTT로 관제한다. GUI에서 상태·위치·Alarm을 확인하고 명령을 요청하며 결과·업무 이력을 조회할 수 있어야 한다. 근거: PDF p2.

## 3. 사용자와 업무

| 사용자 | 업무 | 필요한 결과 |
| --- | --- | --- |
| 관제 사용자 | 상태 확인·이동/정지/복구·조회 | 대상·요청 결과·최신 상태 |
| 검증 담당자 | 장애·통신 이상·복구 재현 | 조건·관측값·원인·증거 |
| 개발 담당자 | 컴포넌트 구현·통합 | 공통 데이터·책임·인터페이스·수용 기준 |
| 설정 담당자 | 수량·시작점·경로·속도·장애 구성 | 코드 수정 없이 시험 구성 |

운영 인증·권한·배포 체계는 원문에 정의되지 않았으며 별도 요구 확정 대상이다.

## 4. 제품 범위

| 범위 | 필수 내용 | 원문 |
| --- | --- | --- |
| 통신 | 송수신·검증·독립 큐·연결/Heartbeat 감시·결과 전달 | p8~9 |
| 가상 AMR | 설정 기반2대 시험, 이동·정지·복구·장애, 실제 데이터/결과 생성 | p10~11 |
| GUI | Dashboard,2D Map,Alarm/History,Detail/Command | p11~14 |
| Core·SQLite | 등록·최신 상태·Alarm·명령·History·저장/조회 | p15~16 |
| 통합 | 정상 운행·명령·장애·통신 복구의 종단 간 검증 | p17 |

초기 시험은2대이며 설정으로 수량을 구성한다.2대 시험을 운영 최대 지원 대수로 해석하지 않는다. 물리 로봇·GPS·고급 경로 탐색·충돌 회피는 필수가 아니다. 화면 예시만으로 PAUSE·배터리·부가 통계를 요구하지 않는다.

GUI는 Mock으로 독립 개발할 수 있지만 최종 인수는 실제 Core·통신·시뮬레이터·DB로 수행한다. 자동 재접속·재구독은 복구 시나리오에 포함하며 상세 정책은 P-05에서 정한다.

## 5. 시스템 책임

가상 AMR ↔ Mosquitto ↔ Communication ↔ Core ↔ GUI 구조다. SQLite는 Core가 저장소 연계 기능을 통해 사용한다. GUI는 Communication/DB에 직접 접근하지 않는다. 근거: p2~3,15.

| 구성 | 책임 |
| --- | --- |
| 가상 AMR | 실제 시뮬레이션 상태·장애·수행 결과 생성 |
| Communication | wire 검증·송수신·순서/독립성·통신 관측 이벤트 |
| Core | 등록·업무 상태·Alarm 생애주기·요청/결과·History |
| GUI | Core 데이터 표시·사용자 입력·명령/조회 요청 |
| SQLite 연계 | 영속 저장·조회·갱신·실패 반환 |
| Broker | 메시지 중계. 업무 실행 완료를 판정하지 않음 |

프로세스 분리·HTTP 여부는 설계 선택이며 논리 책임은 유지한다.

## 13. 우선순위와 개발 조건

필수 기능은 전부 최종 납품 범위다. 현재 개발은 [1차 MVP 계획](../mvp/happy_path_plan.md)을 우선한다. 1차는 AMR2대의 Telemetry → Core → WPF 마커, 화면 MOVE → 실제 이동 → 도착 ACK까지 인메모리로 연결한다. SQLite·History·Alarm·STOP/RESET·자동 재접속·업무 Timeout·전체 Dashboard는 2차다. 24기능 각각의 1차 적용 부분과 2차 잔여 범위는 해당 계획의 범위표를 따른다.

개발 순서는 최소 임시 마커 화면 → 실제 Telemetry/Core → 실제 마커 갱신 → MOVE/ACK → 실제2대 시연이다. 임시 데이터는 초기 UI 확인에만 쓰고 최종 1차 인수에는 실제 가상 AMR·Broker·Core·WPF를 연결한다. 위의 DB 포함 전체 인수 기준은 최종 제품 기준이며 1차 시연 완료를 전체 기능 완료로 판정하지 않는다. 사수 검토용 범위·일정은 [MVP 요약](../reports/mvp_review_summary.md)에 분리했다.

등록, STOPPED 전이, 장애 해제, 완료 ACK, 업무 Timeout 등 관련 P 결정이 필요한 부분은 [비교서](pdf_comparison.md)에 있다. 개발자가 운영 의미를 임의로 확정하지 않는다. 되돌릴 수 있는 기술값은 근거를 기록하고 개발용 프로파일로 검증할 수 있다.

## 14. 완료와 변경 관리

기능명세의 정상·오류·경계 기준과 INT-01~04를 모두 충족해야 전체 완료다. 미정 정책·미측정 성능을 표시한다. 요구 삭제·확장·충돌 해결은 페이지·이유·영향 ID·새 검증을 기록한다.

전달 문서는 [기능명세서](feature_spec.md), [공통 계약](interface_contract.md), [PDF 비교·결정대장](pdf_comparison.md)이다.0.1은 Git 이력에 보존한다. 추적기에는 검토 사실을 DN-11 proposed와 change_log로 남기며, 제품5기능의 계약·상태·revision·verification·실행 증거는 변경하지 않는다.

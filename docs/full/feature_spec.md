# 가상 AMR 관제 시스템 기능명세서

버전0.3, 2026-09-30. [요구사항 정의서](prd.md)의 전체 제품을 구현하기 위한 명세다. 기존 소스 파일·클래스·passing 상태를 알 필요 없이 입력·처리·출력·예외·검증으로 읽을 수 있다. 원문 기능표23개와 p15 도식에서 도출한 CORE-06, 총24개를 포함한다. 0.3은 단계별 적용 안내만 추가했으며 0.2의 기능 본문·93개 AC는 유지한다.

## 문서 적용 방법

매일 개발할 순서는 [1차 MVP 계획](../mvp/happy_path_plan.md)을 따른다. 해당 문서의24기능 범위표로 1차 부분을 고른 뒤 아래 관련 기능만 읽는다. 1차는 두 AMR의 실제 좌표·WPF 마커·MOVE·도착 ACK이며 DB·Alarm·복구 등 전체 기능은 2차다. 각 기능의 일부 구현이나 M1-AC 통과는 아래 전체 AC의 통과를 의미하지 않는다.

각 기능의 요구사항 ID는 R-<기능ID>다. 아래 AC 식별자는 **실행할 수용 시험**이며 통과 증거가 아니다. 원문의 모호함은 [PDF 비교·결정대장](pdf_comparison.md)의 P 항목으로 연결한다. 권고안에 의존하는 AC는 그 안을 채택하거나 대안을 정한 후 기대값을 고정해야 한다.

공통 wire 형식·논리 인터페이스·상태 전이·저장 모델·설정과 시험값은 [공통 계약](interface_contract.md)을 함께 전달한다. 명세의 '합의한' 항목은 그 계약의 결정 목록을 가리키며 개발자가 값을 추측해서 완료 판정하지 않는다.

COM-05는 통신 보존·전달, CORE-04는 실제 요청·결과 업무 관리, INT-02는 전체 연결 검증이다. AMR의 실제 데이터 생성과 Communication의 수신 처리는 별개다. 기능 명세는 최종 제품 목표이며 시험 대역이 최종 제품의 실행 결과를 대신하지 않는다.

S030 보충: 단계별 과제 PDF의 과제1~5 산출물과 이 문서의 연결은 [과제 대응표](assignment_mapping.md)를 따른다. 과제3의 Mock GUI 단독 실행·DataProvider 교체·실제 데이터 연결은 D-GUI-01~03으로 별도 확인한다. 기존24기능 본문·93AC는 유지하며, 이3개 미실행 산출물 기준을 GUI 착수 시 검증에 연결한다.

## COM-02 AMR별 생존 감시

| 항목 | 명세 |

| 결정 경계 | 기존 개발 기준은 DN-10. 신규 미수신/Offline 정책 P-17, 등록 P-06. |

- AC-COM-02-01: Timeout 직전/경계/직후에 정한 이벤트가 발생하며 Payload 시각·벽시계 변경에 영향받지 않는다.
- AC-COM-02-02: A 중단 중 B 정상 수신 시 A만 이상으로 관측한다.
- AC-COM-02-03: 중단 구간마다1회 이상 이벤트와 정상 재수신1회 복구 이벤트를 확인한다.
- AC-COM-02-04: 느린 Core·큐 포화에서도 정상 생존 수신을 관측하고 세션 종료 후 오래된 감시가 동작하지 않는다.

## COM-05 Command와 ACK 전달

요구사항: R-COM-05. 출처: PDF p5,9,16.

- AC-COM-05-03: SUCCESS/FAILURE 의미를 바꾸지 않고 불량 cmdId ACK는 Core에 전달하지 않는다.
- AC-COM-05-04: 요청→발행→AMR수신→ACK→Core까지 ID로 추적한다. 실제 업무 갱신은 CORE-04/INT-02에서 확인한다.

## AMR-02 명령 수신과 이동 수행

요구사항: R-AMR-02. 출처: PDF p4~5,11.

| 항목 | 명세 |
| --- | --- |
| 선행 조건 | 공통 명령 형식, 운행/Alarm 상태, 경로·속도·도착 조건, 상태 전이표를 확정한다. |
| 입력과 시작 사건 | MOVE 목표 X/Y, STOP 또는 RESET, 요청 ID. |

| 출력과 종료 결과 | 실제 위치·속도·State 변화와 요청별 수행 결과. |

| 결정 경계 | P-02/03/04/07/20. 현재 미구현 FAILURE 반환을 최종 제품 요구로 삼지 않는다. |

- AC-AMR-02-01: IDLE에서 유효 MOVE 시 실제 좌표가 변하고 합의 도착 오차 내 종료한다.
- AC-AMR-02-02: 이동 중 STOP 후 다음 시뮬레이션 갱신부터 좌표가 변하지 않고 속도가0이다.
- AC-AMR-02-03: 장애 원인이 남은 RESET은 실패하고 해소 후에는 합의한 정상 상태로 복구한다.
- AC-AMR-02-04: BUSY 신규 MOVE·IDLE STOP·STOPPED 재출발은 확정한 전이표대로 동작한다.

## 전체 인수와 구현 순서

수용 시험은 단위·컴포넌트 통합·실제 Broker·실제 전체 시스템 단계로 구분한다. 공통 계약을 먼저 고정하고 각 기능을 검증한 뒤 INT-01~04를 수행한다. 실제 AMR 하드웨어는 필요하지 않지만 시뮬레이터의 실제 상태 계산은 필요하다.

새 개발 프로젝트는 전체 기능을 추적해야 한다. 기존 저장소에 적용할 때는 현재5개 COM 추적기와 별개로 AMR/GUI/CORE/INT 범위를 등록하고 영향받는 현행 계약의 revision·회귀를 관리한다. 이번 문서 작성으로 실행 기능을 새로 passing 처리하지 않는다.

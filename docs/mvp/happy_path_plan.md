# AMR 관제 시스템 1차 MVP 개발 계획

문서 버전0.3, 2026-09-30. **가상 AMR 2대 → MQTT 좌표 → Core → WPF 마커 → MOVE → 실제 도착 ACK**를 가장 먼저 연결한다. 개발자가 매일 볼 주 문서다. SQLite·Alarm·STOP/RESET·자동 재접속·업무 Timeout은 2차다.

이 계획은 S027의 목록 화면·DB 포함 MVP를 대체한다. 기존 HP 단계ㅌ`와 HP-AC 식별자는 당시 계획으로 보존하며, 이번 계획은 M1 단계와 M1-AC를 사용한다. 제품 구현과 시연은 아직 미실행이다. 전체24기능·93AC는 [기능명세서](../full/feature_spec.md)에 유지한다.

## 2. 완료 기반과 이번에 만들 부분

COM-03 연결·감시, COM-04 입력 검사, COM-01 송수신·AMR별 큐, COM-02 Heartbeat 감시는 기존 passing 범위를 재사용한다. 이미 만든 방어 로직을 제거하지 않는다. 최신 제품 검증은 S024이며 이번 문서 작성의 실행 결과가 아니다.

현재 TestClient는 Heartbeat와 명령 수신·실패 ACK 기본 왕복만 제공한다. 실제 이동·Telemetry 생성은 추가해야 한다. WPF는 실험 화면이며 실제 Core와 관제 화면 연결도 새 작업이다. COM-05는 기본 전달 코드가 있지만 전체 검증은 not_started다.

## 3. 1차와 2차 범위

1차의 정상 조건은 Broker 연결 유지, 설정된 두 AMR, 허용 좌표의 MOVE, AMR당 진행 중 요청1건이다. 두 AMR은 각각 독립 이동한다. “무조건 성공”은 이 조건의 정상 시나리오를 먼저 만든다는 의미다. **받자마자 SUCCESS를 만들지 않고 실제 가상 이동이 끝난 뒤 보낸다.** 프로그램 오류·발행 실패를 숨기거나 ACK가 없는 요청을 성공으로 표시하지 않는다.

아래 표는 전체24기능의 배치다. “일부”는 전체 기능 완료를 뜻하지 않는다.

## 4. 개발 순서와 종료 기준

기존 환경과 스택에 익숙한 개발자1명의 **기본 추정12~17시간**, 통합·학습 여유2~3시간을 더해 **14~20시간, 집중 개발2~3일**을 목표로 한다. 설치·환경 복구나 추가 요구가 생기면 다시 산정한다. 전체24기능의 완료 일정은 아니다.

| 순서 | 구현할 것 | 단계 종료 결과 | 예상 |
| --- | --- | --- | --- |
| M1-00 | 현재 기준선·Broker·통신 연결 확인 | 기존 통신 재사용 가능, 작업 범위 등록 | 1시간 |
| M1-01 | WPF Canvas에 임시 마커2개와 ID 표시 | 창에서 두 점이 보임. 임시 데이터임을 표시 | 1~2시간 |
| M1-02 | AMR Telemetry와 실제 Core 수신·최신 상태 | 두 AMR의 서로 다른 좌표를 Core에서 조회 | 3~4시간 |
| M1-03 | Core 좌표를 WPF 마커에 바인딩 | 임시 공급자를 실제 Core로 교체하고 수신 좌표 표시 | 2~3시간 |
| M1-04 | Core 요청·AMR MOVE·ACK·GUI 버튼 연결 | 클릭→좌표 이동→도착→해당 요청 완료 표시 | 3~4시간 |
| M1-05 | 실제2대 시연·회귀·재시작·실행 안내 | 아래6개 인수 기준 및 영향 검증 증거 | 2~3시간 |

M1은 계획 단계이며 feature_list의 기능 ID가 아니다. 착수 시 전체 기능의 일부인 MVP 추적 범위·검증·의존성을 등록하고 한 번에 하나만 in_progress로 진행한다. 기존 COM-05 기준을 축소하거나 부분 구현한 AMR/GUI/CORE 기능을 전체 passing으로 표시하지 않는다.

### M1-00 시작 확인

[진행 기록](../../claude-progress.md)과 [추적기](../../feature_list.json)를 읽고 프로젝트 루트에서 `./init.cmd verify`, `./init.cmd broker`를 실행한다. 환경 실패와 코드 실패를 분리한다. 새로운 전체 관제 실행 명령은 구현 후 README에 기록한다. 현재 `init.cmd start`는 통신 콘솔 실행이며 관제 GUI 실행으로 안내하지 않는다.

### M1-01 먼저 보이는 화면

기존 WPF 프로젝트에 최소 관제 화면을 추가하고 실험 화면은 보존한다. Canvas와 Ellipse 두 개, ID 라벨, 선택 장비·목표 X/Y·MOVE·명령 상태를 배치한다. 이 단계의 MOVE는 비활성 상태여도 된다. 임시 데이터 공급자를 써서 바인딩을 확인하며, 화면에서 자체 이동시킨 점을 실제 MQTT 연동으로 주장하지 않는다.

좌표 변환의 개발용 제안은 고정된 월드 범위와 축척을 사용하고 `screenX = offsetX + x * scale`, `screenY = offsetY - y * scale`로 Y축을 맞추는 것이다. 마커 중심을 좌표에 맞추고 반지름을 보정한다. 데모 좌표가 화면 안에 들어오도록 설정한다. 배경 지도·줌·팬·차트는 만들지 않는다.

### M1-02 실제 Telemetry와 Core

[Amr.TestClient](../../src/Amr.TestClient/Program.cs)의 기존 연결·구독·Heartbeat를 확장하고 서로 다른 ID의 프로세스2개를 실행한다. 처음에는 정지 좌표·속도0·IDLE을 Telemetry로 발행한다. Topic ID와 Payload ID, 필드·자료형·Unix ms는 채택된 계약을 따른다.

`src/Amr.Core/`는 신규 프로젝트 제안 경로다. 기존 `IIncomingMessageSink`로 검증된 메시지만 받아 AMR별 불변 스냅샷을 교체한다. MQTT 구독·JSON 검사를 Core에 다시 만들지 않는다. 상태 조회와 명령 요청을 Core가 제공하고 GUI는 그 인터페이스만 사용한다. 별도 HTTP 서버나 프로세스 간 통신은 MVP에 필요하지 않다.

설정의 두 ID를 인메모리로 인지하고 최신 수신 순서대로 갱신한다. 여러 필드를 가진 공유 객체를 동시에 수정하지 않는다. Telemetry 갱신이 명령 결과·Heartbeat 관측 값을 지우지 않게 분리한다.

### M1-03 실제 좌표로 마커 갱신

임시 데이터 공급자를 실제 Core 조회로 교체한다. WPF Dispatcher에서 마커 위치와 선택 장비 값을 갱신한다. GUI가 Communication이나 SQLite를 직접 호출하지 않는다. 위치는 Telemetry에서만 가져오며 GUI가 자체 계산한 이동 애니메이션을 실제 로봇 위치로 쓰지 않는다. 서로 다른 초기 좌표의 두 ID가 구분되면 다음 단계로 간다.

### M1-04 MOVE와 완료 결과

1. 사용자가 AMR과 목표 X/Y를 선택한다. Core가 입력과 진행 요청 유무를 확인한다.
2. Core가 고유 cmdId·대상·목표를 보관한 뒤 기존 `MqttPublisher.PublishCommandAsync`로 발행한다.
3. AMR은 IDLE에서 BUSY로 전환해 일정 속도로 목표까지 직선 이동하며 실제 상태의 Telemetry를 발행한다.
4. 마지막 이동량을 제한해 목표를 지나치지 않게 하고 도착 시 좌표 고정·속도0·IDLE로 바꾼다.
5. 받은 cmdId 그대로 SUCCESS ACK를 보내고 Core가 `(amrId, cmdId)`로 원래 요청을 완료한다.
6. GUI는 Core의 결과를 표시한다. MQTT 발행 완료와 이동 완료는 구분한다.

AMR별 진행 요청은1건으로 제한하고 Core 검사와 버튼 비활성화를 함께 적용한다. 다른 AMR은 별도로 명령을 받는다. ACK에 대응 요청이 없으면 다른 요청을 완료시키지 않는다. 미수신 시 대기로 남기며 자동 Timeout·재전송은 2차다. 시험 중 단절되면 성공 처리하지 않고 시연을 중단해 원인을 확인한다.

### M1-05 실제 연결 검증

Broker·가상 AMR2대·Core·WPF를 실제로 연결한다. 제품 단위/영향 회귀와 실제 Broker 검증은 서로 대체하지 않는다. 전체 COM-05 passing은 [기존7개 검증](../full/iteration_01.md)을 별도로 모두 만족해야 한다. 최종 시연에 Mock 공급자나 가짜 SUCCESS가 남아 있으면 MVP 완료가 아니다.

## 5. 1차 시연 인수 기준

아래는 모두 **not_run**이다. 소스 버전·설정·실행 절차·화면·로그·AMR/명령 식별자를 증거에 남긴다.

| ID | 시연 | 합격 기준 |
| --- | --- | --- |
| M1-AC-01 | 두 AMR과 관제 실행 | 실제 Telemetry의 서로 다른 ID·초기 좌표가 마커2개로 표시됨 |
| M1-AC-02 | A 선택 후 MOVE | A 좌표·마커가 단계적으로 바뀌고 명령 없는 B 위치는 유지됨 |
| M1-AC-03 | A 목표 도착 | 도착 전 SUCCESS 없음, 도착 후 동일 cmdId 결과·IDLE·속도0 표시 |
| M1-AC-04 | 두 AMR에 별도 MOVE | 각자 이동하고 완료 순서가 달라도 대상·요청 결과가 맞음 |
| M1-AC-05 | 시뮬레이터·Core·화면 대조 | 좌표 축 방향·ID·선택 대상이 맞고 마지막 Telemetry와 마커 위치가 일치함 |
| M1-AC-06 | 정상 종료 후 재실행 | 수동 소스/데이터 수정 없이 초기 상태로 시작하고 새 MOVE를 수행함 |

실시간성은 시연 중 관측 지연을 기록한다. 운영 성능 SLA를 통과했다고 주장하지 않는다. 초기 개발 제안은 이동 계산100ms·Telemetry500ms, 경과 시간 기반 거리 계산, 서로 다른 초기 위치와 속도1좌표단위/초다. 범위·축척·주기·허용 지연은 착수 시 P-07/21과 함께 기록한다. 기존 Heartbeat5초/500ms·MQTT5/QoS0/Retain false는 채택 범위를 유지한다.

2차는 **COM-05 남은 전체 검증 → 명령 이력과 SQLite → STOP → 업무 ACK 예외 → 재접속·재구독 → Alarm·RESET → 영속 장비 등록·전체 History·Dashboard/지도 상세·전체 통합** 순서를 제안한다. 이미 검증한 항목은 불필요하게 다시 개발하지 않는다. 상세 정책과 일정은 해당 단계에서 산정한다.

시간이 밀리면 화면 꾸밈·차트·DB를 추가하지 않는다. 기존 검증을 지우거나 완료 ACK를 위조해 일정에 맞추지 않는다. 제품 구현을 요청받기 전에는 이 문서 정리를 실제 개발 착수로 처리하지 않는다.

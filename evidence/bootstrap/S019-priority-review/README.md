## 첫 작업의 최소 범위

1. 관제·AMR·진단 도구의 명령 Topic을 `amr/{amrId}/command`로 맞춘다(p6).
2. 현재 콘솔의 `target: STATION-1`만 있는 명령을 p6 예시의 `cmdId/type/ts/param{x,y}`에 맞춘다. STOP/RESET의 param 허용 형태, ID 생성 책임, 각 자료형은 개발용 계약으로 문서화한다. 현재 Int64 Unix 밀리초 계약을 유지하고 PDF 예시 숫자 자릿수만으로 단위를 변경하지 않는다.
3. 요청마다 고유 cmdId를 한 번 만들고 AMR은 재생성하지 않는다(p5). 유효한 ID가 없는 깨진 메시지는 로그 후 폐기하며, 유효한 ID가 있는 거부 가능한 요청은 같은 ID로 실패를 응답한다. 미구현 동작에 성공을 반환하지 않는다.
4. 실패 이유의 전달 계약을 함께 정의한다. p11 AMR-02는 이유가 포함된 ACK를 요구하지만 현재 AckMessage에는 이유가 없고 PayloadValidator는 추가 필드를 거부한다. 필드 이름·선택/필수 조건을 문서화하고 모델·검사기·발행자를 같이 변경한다. 이 변경 시 COM-04 spec_revision을 올리고 전체 회귀 후 passing을 복구한다. 이번 검토만으로 계약을 바꾸거나 통과 상태를 내리지 않는다.
5. Heartbeat 수신 모드가 5초마다 자동 MOVE를 보내는 현 구조는 수동 명령 실습과 분리할 대상으로 기록한다. 정확한 테스트를 위해 명령 요청을 선택적으로 발생시킬 수 있게 한다.
6. JSON/유형/필드/ID 오류 자동 테스트와 실제 Broker 왕복을 실행한다. 순서가 뒤집힌 다중 요청의 완전한 매핑 검증은 COM-05에서, 실제 이동 결과는 AMR-02/04에서 마무리한다.

## 구현 전에 해당 단계에서 정리할 사항

- **실패 이유 ACK**: 위 1단계에서 필드 계약을 정한다. 현재 추가 필드를 거부하므로 AMR 발행자만 고치면 실패 응답 자체가 관제에서 버려진다.
- **ACK 시점**: p5·11은 처리 결과, p10 그림[3]은 명령 처리와 ACK 생성 흐름이 모호하다. 수신했다는 이유로 이동 완료 SUCCESS를 반환하지 않는다. MOVE가 STOP/장애로 중단됐을 때 원래 MOVE 결과를 어떻게 마무리할지도 7단계에서 기록한다.
- **STOPPED 다음 동작**: p4 STOPPED 설명과 p5 명령표를 합쳐도 정상 재출발 경로가 명확하지 않다(MOVE=IDLE, RESET=FAULT). 7단계 착수 때 전이 표를 확정하고 임의로 RESET을 STOPPED에 허용하지 않는다.
- **ERR 장애 상태**: p4 ERR은 FAULT, p5 ALM-COL-001은 '해제조건 확인 후 STOPPED'로 표기되어 있고 전환 시점이 모호하다. 8단계에서 장애 발생/해제/RESET별 전이를 분리해 결정한다. Alarm Level 수신 파서가 State를 강제로 바꾸는 구조로 만들지 않는다.
- **재접속 범위**: DN-04는 자동 복구를 후속으로 미뤘지만 기존 사용자 과제1 설명, p8 그림[2], p17 INT-04에는 연결·구독 복구가 있다. 과제1 최종 시연에서는 누락하지 않는다. 운영 Backoff/QoS/중복 명령 재전송은 개발용 기본 복구와 구분하여 계약 변경 이력을 남긴다.
- **2대 설정·경로**: 목표 좌표와 설정 경로의 관계, 초기 FAULT/장애 원인, 주기 값은 AMR-01/02 착수 시 최소 개발 정책으로 정한다. 고급 경로 탐색·충돌 회피·운영 로봇 안전 정책으로 확대하지 않는다.

## 현재 후순위

GUI 지도/차트, SQLite History, 실제 Core 업무 서비스는 과제3~4다. 과제1·2는 콘솔과 Core 대역으로 먼저 완료·검증할 수 있다. 상세 MqttAlive Ping/Pong, 운영 QoS/중복 처리, 장애 코드 확장은 미정/후속으로 구분한다. 기본 재접속과 재구독 자체를 후순위라는 이유로 생략하지 않는다.

## 두 과제 최종 확인 시나리오

설정으로 2대 시작 → 두 Heartbeat/Telemetry 수신 → 서로 다른 ID로 MOVE → 좌표 변화·도착 결과 확인 → 이동 중 STOP → 장애 발생·Alarm/실패 ACK → 원인 해소·RESET → 한 AMR 종료 감지 → Broker 재시작 후 자동 재연결·재구독·송수신 재개. 잘못된 명령 거부, 순서/독립 처리, 응답 역순 매핑도 별도로 확인한다. GUI/DB/실제 장비 통합 통과로 확대하지 않는다.

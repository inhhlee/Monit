# AMR 관제 시스템 요구사항 정의서

문서 버전 0.1, 작성일 2026-09-30. 가상 AMR 통신·제어·관제 시스템의 전체 목표와 단계별 범위를 정의한다. 현재 적용 계약과 검증 상태는 [기능 추적기](../feature_list.json)가 기준이며, 후속 요구사항은 개발 제안이다. 이 초안 작성은 제품 계약 채택이나 기능 완료를 의미하지 않는다.

## 1. 문서 목적

기획자와 개발자가 같은 완료 장면을 이해하고 요구사항 → 기능 → 작업 → 검증 증거를 연결한다. 사용자 제공 KubeOpsAgent의 PRD·Task·Iteration·Project Guide 구성을 참고하되, 기존 AMR 기술과 아키텍처를 유지한다.

## 2. 제품 개요

독립적인 가상 AMR의 상태를 MQTT로 수집하고 MOVE·STOP·RESET 명령과 결과를 추적하는 Windows 기반 관제 시스템이다. 최종 목표는 장비 등록, 위치·상태 표시, 명령 처리, 장애 확인과 이력 조회를 연결하는 것이다.

## 3. 배경과 문제 정의

현재 통신 계층은 Broker 연결, 네 유형의 메시지 검증·수신, AMR별 큐, Heartbeat 감시를 제공한다. 가상 AMR은 Heartbeat와 실패 ACK를 발행하며 이동·Telemetry·Alarm 생성과 실제 Core·GUI·DB 통합은 후속이다.

Command 발행 성공, AMR 수신 성공, 실행 완료, Core의 결과 저장은 서로 다른 단계다. 메시지가 도착했다는 이유로 실행 완료를 표시하거나, 수신 테스트를 가상 AMR 구현 완료로 계산하지 않아야 한다.

## 4. 목표 사용자

## 5. 제품 목표와 측정 기준

아래는 인수 목표다. 전체 시스템의 달성 결과가 아니며, 성능 목표가 미정인 항목에 임의의 수치를 부여하지 않는다.

| 목표 | 측정 방법 | 현재 근거 |
| --- | --- | --- |
| AMR 독립 처리 | A의 Core 처리 보류 중 B 처리 완료, A 순서 유지 | COM-01 및 S024 회귀 |
| 입력 오류 격리 | 오류 Core 전달 0건, 원인 로그, 이후 정상 수신 | COM-04 |

| 시뮬레이션 관찰 | 실제 좌표·속도·상태와 Telemetry 일치 | 후속 |
| 장애·복구 추적 | 장애 원인·상태·Alarm·명령 결과 일치 | 후속 |

## 6. 범위 정의

| 단계 | 포함 범위 | 완료 경계 |
| --- | --- | --- |
| A 통신 기반 | COM-01~05 연결·송수신·검증·감시·ID 연계 | 실제 Mosquitto와 Core/AMR 대역 검증 |
| B 통신 복구 | 자동 재접속·재구독, 새 송수신 재개 | INT-04 관련 후속 부분 |
| C 가상 AMR | 설정 기반2대, 이동·정지·장애·복구, Telemetry·Alarm·결과 | 실제 시뮬레이터 상태 검증 |
| D Core와 저장 | 등록·현재 상태·요청/결과·SQLite 이력 | 실제 Core와 영속 저장 |
| E GUI와 통합 | Core를 통한 표시·조작·조회 | 실제 컴포넌트로 종단 간 검증 |

물리 로봇 운행, 실제 장비 안전 제어, 고급 경로 탐색·충돌 회피, 운영 규모 부하 보장은 초안 범위 밖이다. GUI 화면과 DB 스키마는 단계 D/E에서 구체화한다.

## 7. 제품 원칙

1. 유효한 메시지만 업무 경계로 전달하고 입력 검증 실패와 업무 History를 구분한다.
2. GUI는 Core를 통해 조회·명령한다. Communication/SQLite에 직접 접근하지 않는다.
3. ID는 요청 측에서 한 번 생성하고 통신 경로는 보존한다. 전체 책임 채택은 DN-06에서 관리한다.
4. Heartbeat 감시, Broker 연결, 운행 상태, 명령 업무 상태를 구분한다.
5. 구현·시험 대역·실제 통합·계획을 구분한다. 수신 성공을 실행 완료로 표시하지 않는다.
6. 한 번에 하나의 추적 기능을 개발하고 계약 변경 시 영향과 재검증을 기록한다.

## 9. 아키텍처 개요

현재는 통신 콘솔 ↔ Communication ↔ Mosquitto ↔ TestClient이며 콘솔이 Core 대역이다. 목표는 GUI ↔ Core ↔ Communication ↔ Mosquitto ↔ 가상 AMR, SQLite는 Core에만 연결한다. [상세 설계](../project_guide/detail_architecture.md)를 따른다.

## 12. 인터페이스와 계약

Topic은 command/ack/heartbeat/telemetry/alarm이다. [Command 계약](../src/Amr.Communication/Command/CONTRACT.md), [수신 계약](../src/Amr.Communication/Validation/CONTRACT.md)과 기능명세서의 표를 따른다. 이번 초안은 wire 필드·enum·revision을 변경하지 않는다.

## 13. 기술과 구현 전략

C#/.NET10, MQTTnet5.2.0.1603, Mosquitto와 기존 Windows WPF 실험 프로젝트를 기반으로 한다. SQLite는 목표 저장소이며 실제 Core 통합은 후속이다. 참고 프로젝트의 Python·Kubernetes·LLM·LangGraph는 AMR 의존성으로 도입하지 않는다.

## 14. 릴리즈 계획

통신 검증 → 자동 복구 → 가상 AMR → Core·저장 → GUI 통합 순의 제안이다. 첫 반복 개발은 [COM-05](iteration_01.md)이며 기존 구현을 처음부터 다시 만들지 않는다. 일정·인력·운영 배포일은 미정이다.

## 17. 출처와 변경 관리

제품 근거는 [AGENTS](../AGENTS.md), 추적기, [진행 기록](../claude-progress.md), 현행 계약과 [과제1·2 검토](../evidence/bootstrap/S019-priority-review/README.md)다. PDF 내용은 기존 검토 기록에 근거하며 이번 세션에서 원문을 재검토하지 않았다.

KubeOpsAgent ZIP은 문서 구조 참고 자료다. 파일 해시와 대응 관계는 [구성 검토 기록](../evidence/documentation/S025-project-structure/README.md)에 남긴다. 새 후속 동작을 채택할 때는 추적기의 설계 결정·revision·검증에 먼저 반영한다.

# AMR 관제 시스템 남은 기능 개발 계획

2026-09-30 기준. 기존 통신 기반을 재사용하여 **가상 AMR 2대의 위치 수신 → 화면에서 MOVE 요청 → 실제 가상 이동 → 완료 ACK → 결과 표시와 DB 이력**을 먼저 연결한다. 이 문서는 남은 개발 순서와 최소 시연 범위를 정한 계획이며 구현 완료 보고가 아니다.

전체 요구사항은 [PRD](prd.md)·[기능명세서](feature_spec.md)에 유지한다. 자동 재접속과 복잡한 업무 예외는 MVP 이후로 옮긴다. 이미 구현한 입력 검사·AMR별 큐·Heartbeat 감시는 계속 사용한다.

## 1. 재사용할 완료 범위

| 기존 기반 | 현재 근거 | 이번에 추가할 부분 |
| --- | --- | --- |
| MQTT 연결·연결 상태 감시 | COM-03 revision2 passing | 새 연결 계층 없이 가상 AMR과 Core에 연결 |
| JSON·Topic·필수 필드 검사 | COM-04 revision4 passing | 기존 메시지 계약에 맞춰 실제 Telemetry 생성 |
| 송수신·AMR별 비동기 큐 | COM-01 revision4 passing | 검증된 메시지를 실제 Core가 소비 |
| Heartbeat Timeout·복구 감지 | COM-02 revision2 passing | 기존 감시를 유지하고 Core에 관측 값 전달 |
| Command 수신·ACK 기본 왕복 | 일부 구현, COM-05 not_started | 실제 MOVE 수행과 요청별 결과 관리 |
| WPF·SQLite 실험 코드 | 개발환경 실험, 제품 통합 미완료 | Core를 경유하는 실제 화면과 이력 저장 |

가상 AMR은 현재 Heartbeat를 발행하지만 실제 이동·Telemetry·Alarm 생성은 없다. 정상 명령에도 SIMULATION_NOT_IMPLEMENTED 실패를 반환한다. 따라서 MQTT 연결부터 다시 만들거나 WPF 실험 화면을 제품 완료로 계산하지 않는다. 최신 검증은 [진행 기록](../claude-progress.md)의 S024이며 이 계획 작성 중 제품 테스트를 재실행하지 않았다.

## 2. MVP 범위와 개발 순서

아래 시간은 기존 환경이 정상이고 C#·WPF·MQTT를 이해하는 개발자 1명의 집중 작업 추정이다. 각 단계의 간단한 확인을 포함하며 마지막 단계는 전체 연결 검증이다. **합계 14~20시간**, 환경 복구·추가 학습 여유 2~4시간을 잡으면 16~24시간이다. 2~3일은 목표 일정이며 전체 명세 납품 일정은 아니다.

| 순서 | 작업 | 구현 범위 | 단계 종료 시 확인할 결과 | 예상 |
| --- | --- | --- | --- | --- |
| HP-00 | 기준선과 연결 지점 확인 | 기존 verify 실행, Broker·AMR 2대 확인, MVP 추적 단위와 임시 설정 기록 | 기존 통신을 그대로 사용할 수 있음 | 1시간 |
| HP-01 | 가상 AMR 상태와 Telemetry | 두 ID·시작 좌표·속도 설정, IDLE 상태와 주기적 좌표 발행, 기존 Heartbeat 유지 | 두 AMR의 정지 좌표가 관제에 별도로 수신됨 | 1~2시간 |
| HP-02 | Core 최신 상태 저장 | 실제 Core 프로젝트, 수신 sink 연결, AMR별 최신 스냅샷 교체·조회 | 같은 ID는 최신 값으로 바뀌고 다른 ID는 유지됨 | 2~3시간 |
| HP-03 | MOVE와 실제 완료 ACK | Core의 cmdId 생성·요청 보관·발행, AMR 직선 이동, 도착 ACK, Core 결과 연결 | 좌표가 변하고 도착 후 해당 요청만 SUCCESS로 바뀜 | 3~4시간 |
| HP-04 | 최소 WPF 관제 화면 | AMR 목록·좌표·운행 상태·명령 결과, 대상 좌표 입력과 MOVE 버튼 | 화면에서 보낸 MOVE의 이동과 완료를 확인함 | 3~4시간 |
| HP-05 | SQLite 명령 이력 | 요청/결과를 한 이벤트 테이블에 INSERT, Core를 통한 이력 조회 | cmdId로 요청·결과가 연결되고 재실행해도 조회됨 | 2~3시간 |
| HP-06 | 실제 연결 시연과 인수 기록 | 실제 Broker·가상 AMR 2대·Core·WPF·DB, 표준 검증·영향 회귀·실행 안내 | 아래 6개 MVP 시나리오와 증거 확인 | 2~3시간 |

HP 번호는 시연 단계다. 기능 추적기의 상태 ID와 혼용하지 않는다. 실제 구현 착수 시 전체 기능의 일부임을 명시한 작업 범위·검증 항목·의존성을 등록하고 한 번에 하나만 in_progress로 진행한다. 여러 기능에 걸친 단계도 하위 작업을 순차 완료한다. 현재 제품 기능 상태는 이번 계획에서 바꾸지 않는다.

## 3. 단계별 구현 메모

### HP-00 기준선 확인

[진행 기록](../claude-progress.md)과 [추적기](../feature_list.json)를 읽고 프로젝트 루트에서 `./init.cmd verify`, `./init.cmd broker`를 실행한다. 환경 실패 시 원인과 복구 시간을 분리한다. MVP에서 사용할 두 ID·초기 좌표·속도·주기와 ACK 의미를 기록한 후 구현한다.

### HP-01 가상 AMR 데이터 생성

[Amr.TestClient](../src/Amr.TestClient/Program.cs)의 기존 연결·구독·Heartbeat를 확장한다. 별도 프로세스 2개로 실행하고 각각 독립된 상태를 가진다. 이 단계에서는 정지 상태의 Telemetry만 보내도 된다. 이동은 HP-03에서 명령과 연결한다. 정지 상태의 속도는 0이고 Topic ID와 Payload ID는 같아야 한다. JSON 필드·상태 값·Unix 밀리초는 현재 계약을 따른다.

### HP-02 Core 상태 관리

`src/Amr.Core/`는 신규 생성할 제안 경로다. 기존 `IIncomingMessageSink`를 구현해 Communication이 검사한 메시지만 받는다. MQTT 구독과 JSON 검사를 Core에 중복 구현하지 않는다. `ConcurrentDictionary`에는 AMR별 불변 스냅샷을 교체하고 GUI에는 조회 결과를 제공한다. 수신 순서 기준 최신 값으로 단순화하되 여러 필드를 가진 공유 객체를 동시에 수정하지 않는다.

MVP 장비 목록은 동일한 설정의 두 ID로 시작한다. 자동 장비 발견·DB 장비 등록은 후속이다. Heartbeat·Telemetry·Command 결과를 별도 필드로 관리하여 위치 갱신이 연결 관측 값이나 명령 결과를 지우지 않게 한다. Broker 연결 상태와 AMR 운행 상태도 구분한다.

### HP-03 MOVE와 ACK

1. Core가 고유 cmdId와 대상 AMR·좌표를 보관한 다음 기존 `MqttPublisher.PublishCommandAsync`로 발행한다.
2. AMR은 IDLE에서 MOVE를 받아 BUSY가 되고 일정한 속도로 현재 좌표에서 목표 좌표까지 직선 이동한다. 경로 탐색·충돌 회피는 추가하지 않는다.
3. 이동 중 Telemetry에 실제 좌표·속도·상태를 넣는다. 목표를 지나치지 않게 마지막 이동량을 제한하고 도착하면 좌표 고정·속도 0·IDLE로 바꾼다.
4. **도착 후** 받은 cmdId 그대로 SUCCESS ACK를 보낸다. 수신 즉시 SUCCESS를 보내는 시험 대역은 실제 완료 판정에 쓰지 않는다.
5. Core는 `(amrId, cmdId)`로 원래 요청의 결과만 갱신한다. 미요청 ACK가 다른 요청을 완료시키지 않도록 기본 일치 검사는 유지한다.

처음에는 AMR당 진행 중 명령을 하나로 제한하고 Core에서도 중복 요청을 막는다. 서로 다른 두 AMR의 MOVE는 독립 실행한다. 발행 호출 완료는 실행 완료가 아니다. 요청 대기 상태와 결과를 구분하며 ACK가 안 오면 성공으로 바꾸지 않는다. 자동 Timeout·재전송·늦은 ACK 업무 정책은 후속이다.

COM-05의 전체 검증은 [Iteration01](iteration_01.md)에 남긴다. MOVE 시연은 그 일부만 확인한다. STOP/RESET 실제 수행은 후속이며, 지원하지 않는 명령을 성공 처리하지 않는다.

### HP-04 WPF 화면

기존 WPF 프로젝트에 관제 화면을 추가하는 방향으로 시작하고 실험 화면은 보존한다. 처음에는 DataGrid의 ID·X·Y·운행 상태·최근 명령 결과와 목표 X/Y 입력·MOVE 버튼이면 충분하다. 지도·차트·Alarm 화면은 뒤로 둔다.

GUI는 Core의 조회·명령 인터페이스만 사용한다. Core에서 받은 스냅샷을 UI Dispatcher에서 바인딩 값으로 반영한다. MQTT 이벤트에서 직접 화면 컬렉션을 수정하거나 GUI에서 SQLite를 호출하지 않는다. 선택 AMR에 대기 명령이 있으면 버튼을 비활성화하며 이 표시는 Core의 중복 요청 검사와 일치해야 한다.

### HP-05 SQLite 저장

Core가 저장소 인터페이스를 호출해 명령 요청과 결과를 단일 이벤트 테이블에 각각 추가한다. 제안 최소 컬럼은 `eventId`, `occurredAt`, `amrId`, `cmdId`, `eventType`, `commandType`, `targetX`, `targetY`, `result`, `reason`이다. 요청 행에는 결과가 없고 결과 행에는 수신 결과를 남긴다. 파라미터 바인딩을 사용하고 DB가 없으면 초기 스키마를 생성한다.

먼저 cmdId별 조회 또는 최근 이력 목록만 제공한다. 모든 Telemetry를 저장하거나 장비·Alarm·상태변경 이력을 함께 완성하려고 하지 않는다. 검증 실패 Log와 업무 History도 구분한다. 저장 실패는 기록하고 성공으로 표시하지 않되 영속 큐·자동 재시도·보관 정책은 후속이다. 재실행 후 이력 조회는 확인하지만 진행 중 명령의 자동 복원은 MVP 범위가 아니다.

## 4. 구현 시 기록할 개발용 선택

아래는 이 계획의 제안이며 운영 정책이나 기존 계약 변경으로 채택한 값이 아니다. [정책 대장](pdf_comparison.md)의 해당 항목과 함께 착수 시 결정한다. 되돌릴 수 있는 개발 설정 때문에 모든 운영 정책 확정을 기다릴 필요는 없다.

| 항목 | MVP 제안 | 관련 정책 |
| --- | --- | --- |
| 명령 ID·매핑 | Core 생성, 전송 계층 보존, AMR+cmdId 매핑 | P-01, DN-06 |
| MOVE 완료 | 도착 후 SUCCESS, 이동 상태 IDLE→BUSY→IDLE | P-02/07 |
| 데모 좌표·속도 | 시작 A=(0,0), B=(10,0), 속도 1좌표단위/초, 목표는 서로 다른 점 | P-07 |
| 시뮬레이션·발행 | 이동 계산 100ms, Telemetry 500ms 제안, 경과 시간으로 거리 계산 | P-07/21 |
| 초기 장비 | 설정에 있는 두 ID를 Core가 인지, 자동 등록은 후속 | P-06 |
| 요청 대기 | AMR당 1건, 자동 재전송 없음, 시연 중 단절은 실행 중단 후 원인 확인 | P-05/08 |
| 저장 | 명령 요청·결과 이벤트만 단일 테이블, Unix ms Int64 | P-09/10 |

Heartbeat 기본 5초/500ms와 MQTT5·QoS0·Retain false는 기존 채택 범위를 재사용한다. 미래의 값 제안과 혼동하지 않는다. 실제 동작 계약·수용 기준이 바뀌면 영향 기능의 revision과 회귀 범위를 갱신한다.

## 5. MVP 시연 합격 기준

모든 항목은 현재 **not_run**이다. 실제 Core·가상 AMR·GUI·DB를 사용하고 Broker 로그·관제 결과·DB 조회·화면 증거를 함께 남긴다.

| 번호 | 시연 | 합격 기준 |
| --- | --- | --- |
| HP-AC-01 | 두 AMR 실행 | 두 ID·초기 좌표가 각각 표시되고 Heartbeat와 Telemetry가 수신됨 |
| HP-AC-02 | A에 MOVE | A 좌표가 단계적으로 변하고 명령을 받지 않은 B의 좌표는 유지됨 |
| HP-AC-03 | A 도착 | 도착 전 SUCCESS 없음, 도착 후 동일 cmdId 결과·IDLE·속도0 확인 |
| HP-AC-04 | 두 AMR에 서로 다른 MOVE | 각각 독립 이동하고, 다른 거리로 완료 순서가 바뀌어도 원래 요청에 매핑됨 |
| HP-AC-05 | 이력 조회 | 각 cmdId의 요청·결과 행과 대상·좌표·결과가 일치함 |
| HP-AC-06 | 정상 종료 후 재실행 | 코드/DB 수동 수정 없이 시작하고 과거 이력 조회 및 새 MOVE 가능 |

기존 입력 검사·큐·Heartbeat의 영향 회귀와 표준 기준선도 통과해야 한다. 위 항목을 통과해도 전체 AMR/GUI/CORE/INT 기능을 passing 처리하지 않는다. COM-05는 기존 7개 verification을 모두 실행하고 유효 증거를 등록해야 별도로 passing 판정할 수 있다.

## 6. 2일에서 3일 작업 배치

| 작업일 | 목표 | 끝날 때 볼 수 있는 결과 |
| --- | --- | --- |
| 1일차 | HP-00~02, HP-03 착수 | 두 AMR Telemetry가 실제 Core에 쌓이고 조회됨 |
| 2일차 | HP-03~04, 여유가 있으면 HP-05 | WPF에서 MOVE를 보내 이동과 완료를 확인함 |

시간이 밀리면 지도·디자인·차트를 추가하지 않고 위 최소 흐름을 먼저 끝낸다. 검증을 생략해 날짜를 맞추지 않는다.

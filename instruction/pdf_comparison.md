## 1. 도출 원칙

이전 문서0.1은 현재 프로젝트의 구현·계획 안내였다. 개정 요구사항/기능명세0.2는 새 개발자가 구현해야 할 전체 제품을 정의한다. 현재 클래스명·테스트 개수·passing 상태를 요구사항 본문에서 제거하고 원문 기능 ID, 입출력, 예외, 수용 기준으로 재구성했다.

S028의 문서0.3은 이 원문 대조 결과와 전체 기능 기준을 유지하면서 [1차 MVP 계획](happy_path_plan.md)의 단계 구분을 추가했다. 1차는 실제 좌표 마커·MOVE·도착 ACK이며 DB·Alarm·복구는2차다. 아래0.2 표는 원문에서 전체 요구를 도출한 당시 비교 기록으로 보존한다.

| 표시 | 의미 |
| --- | --- |
| 원문 | PDF가 요구하는 기능과 의미. 구현되지 않았어도 납품 범위 |
| 기존 결정 | DN에 이미 기록된 개발용 계약. PDF 확정값과 구분 |
| 도출 | 원문을 시험 가능한 행동·수용 기준으로 풀어 쓴 내용 |

새 문서 작성으로 현재 feature_list의5기능·revision·실행 증거를 변경하지 않는다. 현 저장소 구현에 새 계약을 적용할 때는 설계 결정과 추적기 개정·회귀가 먼저 필요하다.

## 5. Alarm 예시의 해석 한계

p5 ALM-OBS-001은 거리≤1.0m 발생, 거리>1.2m가2초 지속하면 해제라는 예시다. ALM-COL-001은≤0.5m 발생이나 해제 칸의0.7m는 부등호·유지시간이 없다. ALM-EMG-001은 비상 정지/Heartbeat 응답 초과와 RESET을 혼재한다. p4의 WARN3회 ERR 설명과 p5 거리 기반 ERR도 서로 다른 규칙이다.

이 숫자들을 전체 장애 정책의 확정값으로 복사하지 않는다. 장애 시나리오 설정의 예시 데이터로 보존하고 P-04에서 코드별 발생/해제·시간·동시 Alarm·우선순위를 확정해야 한다. 단위 테스트는 확정된 임계값 직전/경계/직후와 유지시간 경계를 검증한다.

## 6. 기존 구현과 목표 요구사항의 차이

| 영역 | 현재 저장소의 기록상 범위 | 전체 제품에 남은 일 |
| --- | --- | --- |
| COM-01~04 | 현행 개발 계약의 통신·검증·큐·Heartbeat passing | 채택될 정책 변경 시 재검증, 운영 범위 확정 |
| COM-05 | 기본 왕복/ID 보존, 전체 기능 not_started | 다중 요청 연계 증거 및 Core 업무 통합 |
| 가상 AMR | Heartbeat·명령 수신·미구현 FAILURE | 이동·상태·장애·실제 결과·Telemetry/Alarm |
| Core/SQLite | 실험 및 수신 대역과 구분 필요 | CORE-01~06 실제 업무·저장 구현 |
| GUI | WPF 실험 코드 | GUI-01~04 계약·Mock 개발·실제 Core 연결 |
| 통합 | 부분 통신 시험 | INT-01~04 전체 종단 간 검증 |

현재 미구현 항목도 제품 요구사항에서 삭제하거나 단순 선택 확장으로 내리지 않는다. 기존 S025의 개발 순서는 이 저장소 재개 전략이며 원문 납품 범위와 별개다.
